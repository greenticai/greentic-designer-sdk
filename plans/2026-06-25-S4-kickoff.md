We are continuing the **ComponentExtension adapter** epic. Two foundational slices are already
MERGED to `research`: `component_tools` admin registration (greentic-admin #274) and
`resolve_component` (greentic-component #88). Now build **S4: the designer adapter**.

**Before doing anything, re-ground (do NOT trust memory blindly — verify against current code):**
1. Read `greentic-designer-sdk/plans/2026-06-25-component-extension-adapter.md` (full plan,
   frozen contracts in Appendix A, and the Progress log — note every "verified" finding).
2. Read the memory file `component-extension-adapter-epic.md`.
3. Re-confirm the merged APIs still exist as described: the admin endpoint
   `GET /api/v1/designer/tenant/me/component-tools` (greentic-admin) and
   `greentic_component::resolve::resolve_component(url, cache_dir)` (greentic-component, behind
   `store`+`describe` features).

**Goal of S4:** In the `greentic-designer` repo, build a `ComponentToolSource` that:
- reads the per-tenant registered `component_tools` from the admin API (already merged),
- for each registered component, calls `greentic_component::resolve::resolve_component` to
  discover its operations (the designer process already runs wasm via ext-runtime, so
  introspection belongs HERE — NOT in admin, which deliberately refuses in-process wasm),
- surfaces those operations as agentic-worker tools in the dw-composer tool picker, each with
  `extension_id = "component:<ref>"` (the frozen ToolRef convention the runtime already
  dispatches — see Appendix A Contract #3), so a composed `AgentConfig.tools` entry is callable
  by the runtime with zero further wiring.

**Hard constraints / findings already verified (don't re-litigate, but DO re-verify if you
touch the area):**
- Tool **descriptions**: components carry no description today (WIT `///` docs are stripped by
  the build; no manifest description field yet). Decision = **name-now**: synthesize from the
  operation name (the runtime fallback already does this). Authored-description (option 2) is a
  separate, Maarten-gated slice that would re-open the release-train — do NOT depend on it.
- Tool **input_schema**: NOT derivable from a URL'd bare wasm — it lives in the component
  manifest, supplied by the registrant. `resolve_component` returns operation NAMES only.
  Decide in S4 how the composer handles schema-less tools (e.g. permissive object schema, or
  require the registrant to supply `operations[]` with schemas via the admin API which already
  accepts them).
- Mirror the existing **MCP** surfacing path in the designer (`McpToolSource` /
  `ui/mcp/catalog/snapshot.rs`, `extensions.rs::list_tools_by_capability`) — that is the proven
  template. Keep `(component_ref, operation)` tuple keying, like MCP and the runtime do.

**Working discipline (this epic has burned us twice on false-green — hold the line):**
- Reuse-first: check shared crates/existing sources before writing new code.
- TDD; verify by READING cargo's text output, never the piped exit code (`cmd | tail` masks
  cargo's exit — a real failure can show "exit 0").
- A passing test built on hand-fabricated data is NOT proof — prefer end-to-end tests over real
  fixtures (that is how we caught the WIT-docs and OCI-stub issues).
- `greentic-designer` origin is greentic-biz; PRs target `research`; NO Claude/AI co-author
  trailer on commits or PR bodies. Rebase onto `origin/research` before PR (research diverges).
- i18n: any new designer strings must touch all 5 locales (en/es/id/ja/zh) or
  `locale-parity.test.ts` fails.
- Disk fills fast here (per-repo target dirs are huge) — `cargo clean` an already-verified repo
  if you hit "No space left on device".

**Plan it first:** S4 is multi-part (designer backend source + composer UI + tests + i18n).
Start by exploring how the designer loads tool sources and how dw-composer renders the tool
picker, then propose a slice breakdown before implementing.
